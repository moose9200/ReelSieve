## Decisions (what + why + what was rejected)
- Paid orders keep a billing email snapshot (orders.billing_email, set when paid) for FINANCIAL_RECORDS_YEARS = 8 from payment, then the row is deleted. Why: CGST s.36 (72 months from the annual-return due date) and Income-tax Rules 2026 r.46 (7 tax years from the end of the tax year) both end within 8 years of any payment date (legal report §6). Rejected: exact per-rule dates (more code, same outcome). Records under appeal/investigation need a manual hold.
- An order the customer reported paid before erasing keeps a billing email snapshot too, so a payment that clears later is recorded against the payer; if it is still unpaid 90 days after erasure it is deleted (code review finding, fixed with test_an_order_reported_paid_before_erasure_keeps_the_payer_email_when_settled_later).
- Erasure keeps the users row (anonymised, erased_at) because orders/usage/admin_events point at it; jobs, outreach, Drive receipts, OAuth states and unpaid orders are deleted; usage keeps counts, drops listing key; its ip_hash stays until the normal 90-day purge (abuse window).
- Signal and suppression keys are derived from SESSION_SECRET with purpose labels. Rotating SESSION_SECRET resets free-tier network counts and stops old objections matching: re-key outreach_suppressions before any rotation.
- Outreach retention is 12 months after the last change (brief); the legal report proposes ~90 days (I) - Hemant to decide.
- Image proxy allowlist is a0.muscache.com only (the only CDN host in listing, search and co-host data); add hosts when seen.
- India backup = one full snapshot per UTC day at invoices/YYYY/MM/YYYY-MM-DD.csv (ref, date, plan, amount, currency, provider, status, paid_at, billing_email; paid orders only). Why full snapshots: each file alone restores the paid-order records (not refunds: those live only in the payment provider; the Settings hint says to keep its refund reports in India too). The worker reads the bucket lifecycle before every upload and refuses unless an enabled prefix-only rule expires the key within 90 days, so an order deleted by retention at 8 years is gone from backups within 90 days more (notice: "deleted 90 days after each copy is made"). Versioning is not read (needs s3:GetBucketVersioning): setup says keep it off. IAM user: s3:PutObject on invoices/* only with If-None-Match (condition s3:if-none-match) + s3:GetLifecycleConfiguration; no Get/Delete, so the key cannot read, overwrite or delete past days. A 412 is recorded as a failure, not ok, so a file planted ahead of time is visible. AWS endpoints must be *.amazonaws.com naming ap-south-1/ap-south-2 (global and other regions refused); other https endpoints need INVOICE_BACKUP_ENDPOINT_IN_INDIA=1. Non-public DATABASE_SCHEMA writes under invoices/<schema>/. CSV is QUOTE_ALL and every cell or ';' ',' tab/line-break segment starting = + - @ tab CR LF or a full-width = + - @ gets ' (OWASP CSV injection). Run records (no personal data) kept 2 years. Rejected: an AWS SDK (new dependency for one PUT), app-side deletion of old files (would need s3:DeleteObject on the key).
- Referrals (feature/referrals): invite code in the link and a hidden signup field only (no referral cookie or browser storage, so no consent needed under PECR reg 6); no email/SMS/DM/share buttons or pre-written messages (ICO "instigating"); Account copy says share publicly and not in unsolicited messages. Both accounts get 1 bonus video when the invited account's first reel is delivered (jobs.finish, savepoint so a referral error never undoes a delivery); no reward for self (any shared network hash from free videos, sign-ups or sign-ins; the same Drive Google account as the inviter; a Google account that already earned an invite reward), removed/on-hold/erased accounts, or past 10 rewards per inviter per UTC calendar month; all decided at the first delivery, never at signup. Export shows a neutral status (pending/rewarded/not_rewarded), never the refusal reason (UK GDPR Art 15(4)).
